When there is no API, you build one

Driving the Google Sites editor straight from your catalogue — what is allowed, what actually works, and the one line you never cross.

Background

The promise you already made

You told a client to use Google Sites, and that was probably the right call, because she can edit it herself afterwards and it costs her nothing whatsoever to run.

Then the last module told you that no software on earth can write a page into Google Sites. So you have a catalogue with two hundred rows in it, a client who is waiting, and no supported way to move one into the other.

This is the module where you stop waiting for a vendor and build the missing piece yourself.

What you are actually building

Get the framing right, because it changes how you talk about this and it changes what you charge.

An application programming interface is simply an agreed way for one program to ask another program to do something, and Google built one for Drive and another for Sheets. They declined to build one for Sites.

So you are going to build your own, and it will work exactly the way a person works, opening the editor, clicking Insert, typing the headline, pasting the paragraph, and moving on to the next row in the sheet.

That is not a hack and it is nothing to be sheepish about, because every automation ever built began with somebody deciding that a repeated human task should stop being done by a human.

The sentence to keep in your head

The vendor did not build a door, so you are walking your work through the front entrance, exactly the way a person does. You are not breaking in.

Which brings us straight to the only rule that genuinely matters here.

The one line you do not cross

Read the terms rather than guessing at them, because the answer is clearer than most people expect.

Google's terms of service say nothing at all about automating your own editing, and what they actually prohibit is "bypassing our systems or protective measures". The Workspace policy uses almost identical language, prohibiting anything that would "circumvent any aspect of the Services".

Anthropic's own usage policy says the matching thing from the opposite direction, prohibiting actions that "circumvent the guardrails or terms of other platforms or services".

Both companies, working independently, drew that same line in precisely the same place, so here it is in plain words.

The actWhere it stands
Editing a site you are an invited editor ofOrdinary work. No rule touches it
Doing that editing with software instead of fingersStill ordinary work
Making an automated browser pretend to be a person so it can get past a loginOver the line, on both policies

Everything sold as a "stealth" tool exists to do that third thing, and every guide telling you to fake a browser signature or add random pauses so you appear human is teaching you the same.

Do not do it, and not primarily because you might be caught, but because you would be selling a client something built on a rule you knowingly broke, which is a miserable foundation for a care plan.

The rule this creates

You never automate the sign-in. Ever.

Which sounds like it ends the module, and it is actually the thing that makes the rest of it work.

Drive the browser that is already signed in

Here is the move that solves the whole problem: do not open a fresh browser and teach it to log in, but use instead the browser the human has already logged into.

Claude Code does exactly this, because you start it with a flag and it opens tabs in your own Chrome, carrying your own signed-in session along with it.

Anthropic's own documentation describes it plainly, saying the tool shares your browser's login state, so it reaches any site you are already signed into. When it meets a login screen or one of those "prove you are human" boxes, it stops and hands the keyboard straight back to you.

Read that last part twice, because the people who built it decided deliberately that the login should stay human. That is the identical line Google drew, honored by the design itself rather than by your good intentions.

What you need for it, checked in August 2026:

  • Chrome, Edge, or another Chromium browser. Not available inside the Windows Linux layer.
  • The Claude in Chrome extension, version 1.0.36 or newer.
  • A direct Anthropic plan: Pro, Max, Team, or Enterprise. It does not run through the cloud resellers.
  • Signed in through the login command. Sessions started with an API key have the browser tools switched off.
Do not reach for screen control instead

There is a separate feature that watches your screen and moves your mouse, and although it sounds like the more powerful option, it is the wrong tool here.

Anthropic's own guidance routes browser work to the Chrome route first, and their documentation notes that screen control treats browsers as view-only. It also warns that the model can guess coordinates wrongly, and says outright not to use it for tasks needing perfect precision.

Dropping an element into an exact spot on a grid is a task needing perfect precision.

There is one more piece of stale advice worth killing off, because older guides tell you to start Chrome with a remote debugging switch and attach to it. Chrome changed that in March 2025 and it no longer works against your normal profile, yet half the tutorials online are still teaching it.

Two tests before you promise anything

This is the professional habit the whole module is really teaching, which is to find out first and promise afterwards. Both tests together take an afternoon.

Test one: build a page using only the keyboard. Open the editor, put your mouse away, and try to add a text box, position it and resize it using nothing but keys, because whatever you cannot do by hand, software cannot do either.

Test two: watch what the recorder sees. Playwright ships a recorder that follows your clicks and prints out how it would find each thing you touched.

If it names buttons by their labels, you are in business, because labels survive a redesign. If it prints strings of scrambled letters instead, stop and rethink, because those change without warning and your script dies silently on a Tuesday.

Ten minutes of this is worth more than a week of hopeful building.

What test one will find

Google publishes keyboard shortcuts for the Sites editor and almost nobody knows they exist, yet they are the quiet centre of this entire approach.

KeysWhat happens
Tab and Shift-TabMove between the things on the page
EnterGrab a section, an embed, or a page
Arrow keysMove the grabbed thing
Alt and an arrowResize a grabbed embed
EscLet go
Spacebar, then arrowsGrab a page and nest it under another
Control, Alt and 1, 2 or 3Turn text into a title or a heading

Look at what that gives you: grab, move, release. That is drag and drop with no dragging in it, published by Google and intended for people who cannot use a mouse.

It is also, and this is the part that genuinely matters, an interaction Google supports deliberately. You are not simulating a mouse at all, you are using the editor the way it was built to be used.

Why the keyboard beats dragging every time

Dragging under automation is genuinely one of the hardest things in this trade, and the reason is worse than mere difficulty.

The main tool has a built-in drag command, and against many modern web applications it does nothing at all and then reports that it succeeded.

Sit with that for a second. Your script says every step passed, the client's page is empty, and you have no error to read and nowhere to start looking. For somebody who cannot read a stack trace, that failure is close to unrecoverable.

The workaround people use is to move the mouse in several small steps rather than one jump, and it does help. But you are still guessing at coordinates on a grid that reflows, and you are still one layout change away from dropping a menu into a footer.

The keyboard has none of those problems, because Enter grabs, arrows move, and Esc lets go. It either worked or it did not, and you can see immediately which.

The order to build in

Never reposition anything, because if you build in the order you want the finished page to read, there is nothing left to move.

  1. Pages first. Every page named, in order, nested where your catalogue says.
  2. Sections next, one per block of content, so each block has its own container.
  3. Content top to bottom, straight down the catalogue by your Page and Order columns.
  4. Embeds last, because a published Sheet or a chart is a single insert and it keeps working afterwards.
  5. Stop. Do not publish. Leave it in draft.

That fifth step is not caution for its own sake, because Google keeps the draft and the published version apart and shows them side by side, so you can see every unpublished change before anybody else does.

One setting will stop your run dead

Google Sites has a setting, on by default, that requires an editor to review changes before publishing.

That inserts an extra screen your automation was not expecting, so either switch it off in the publish settings or write the review step in deliberately. Do not let it surprise you in front of a client.

Write down what happened

Whatever you build, turn on the recording from the very first run. The tooling can keep a full trace, a video, and a screenshot, and you can set all three to save only when something fails.

That costs you nothing on a good day, and on a bad day it gives you a scrubbable recording of the failure. The habit worth teaching is simple: look at the moment just before it broke. That single frame turns "it does not work" into "the Insert button moved."

What stays human, permanently

Be honest with yourself about this list, because pretending it is shorter is how projects go wrong.

Judgment about what looks right. Software places things obediently, and it does not notice that the photo above the menu is unpleasant.

The publish click. A person looks at the draft and decides. Anthropic's own guidance says to keep a human in front of anything with real consequences, and your client's public website qualifies.

Anything needing pixel accuracy. If the layout demands an element in one exact place, do that by hand and stop fighting.

The repair. When Google changes the editor, and they certainly will, absolutely nothing warns you, so a person opens it, looks, and fixes the step that broke.

How new this actually is

I looked for other people doing this, and I want you to know what I found, because it changes how you should price and promise.

Almost nobody has published anything about automating the Google Sites editor, meaning no projects worth reading, no write-ups, and no worked examples. One automation company has a page claiming to support it, and on inspection that page is a template they publish for hundreds of products, with nothing specific to Sites on it at all.

So either it is not worth doing, or everyone who tried gave up quietly and told nobody. Both readings argue for the same thing: build it on your own site first. Not the client's. Yours.

The thing that removes most of the need

Before you build any of this, ask the question that might cancel the project.

How much of this content is ever going to change?

Because a published Google Sheet embedded in a Google site keeps updating on its own, and Google's own wording is that the change "might take a few minutes." A checkbox controls it, on by default, though it does not apply to Slides.

So the prices, the hours, the roster, the schedule and the stats table: none of that needs automating at all, because the client edits a spreadsheet she already understands and her website follows. No script, no maintenance, nothing to break.

That leaves the automation with exactly one job, which is the one-time build. Which is the honest scope, and it is a smaller and much safer promise than the one you were about to make.

What you tell the client

Say this before you touch anything, and put it in writing.

We build the site once, with assistance, using your own signed-in browser and your own account. You add me as an editor and you can remove me at any time. Anything that needs to change regularly lives in a spreadsheet you control, and the site updates itself from it. I do not store your password. I do not pretend to be a person to get past Google's login. If Google changes their editor, I fix it by hand.

Every sentence in that paragraph is a promise you can keep, which is the only kind worth making.

What you actually do on Monday

  1. Run both tests on your own site, not a client's. Keyboard-only build, then the recorder.
  2. Sort your catalogue by the Page and Order columns from Module 26, and read it top to bottom. That reading order is your build order.
  3. Ask the cancelling question. Anything that changes goes in an embedded Sheet and comes out of the automation entirely.
  4. Build the smallest thing that works: one page, three text blocks, straight from three rows.
  5. Leave it in draft and look at it. If the smallest thing works, widen it. If it does not, you have lost an afternoon rather than a client.

That is the whole method, and notice that it is the same method as Module 23. Test small before you bet big. This is simply what that looks like when the thing you are testing is a machine you built yourself.

That gets the site built. Keeping it true afterwards, when the client is editing it too and nobody is telling anybody, is a different problem with a different answer, and it is the last module in this part.

Check yourself

Three questions, no score, nothing recorded. Answer each one in your head first, then reveal. Trying to recall something is what moves it into memory — rereading does not, which is why reading it again feels productive and is not.

1. Where exactly is the line between automating your own editing and breaking the rules?

The editing itself is ordinary work and no rule touches it. The line is bypassing a protective measure — making an automated browser pretend to be a person so it can get past a login. Google's terms and Anthropic's usage policy both prohibit that, independently, in almost the same words.

2. If you never automate the sign-in, how does the automation reach the client's site at all?

You drive the browser the human already signed into. Claude Code started with the Chrome flag opens tabs in your own Chrome carrying your own session, and it pauses and hands the keyboard back when it hits a login or a human-check box. The login stays human by design.

3. Why build with the keyboard instead of dragging elements into place?

The built-in drag command often does nothing against modern web apps and then reports success, which leaves you with a passing script and an empty page. Google publishes keyboard shortcuts for the Sites editor — Enter grabs, arrows move, Esc releases — so it either worked or it visibly did not.
